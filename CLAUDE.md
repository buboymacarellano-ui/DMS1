# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Auto repair shop DMS (dealer/shop management system) for a multi-branch Cebu operation. Server-rendered Express 4 + EJS. No build step, no test suite, no frontend framework. Node >= 22.5.0.

## Commands

```bash
npm run dev            # nodemon app.js (port 3000)
npm start              # node app.js
npm run start:admin    # same app, PORT 3001
npm run start:gm       # same app, PORT 3002
npm run backup         # scripts/backup-app.js (BACKUP_RETENTION_DAYS honored)
```

`start:prod` and `backup:retain30` use Windows `set` syntax — on macOS/Linux use `NODE_ENV=production node app.js`.

No linter, no tests. Verify by running the app and hitting routes.

Data scripts (all in `scripts/`, most take `--dry-run`; see `package.json` for the full list):

```bash
npm run migrate:sqlite                 # JSON -> SQLite
npm run import:transactions            # add --replace to wipe first
npm run flow:branch-parts-10pct        # request -> PM approve -> receive simulation
npm run seed:wo-txdb-1000              # seed 1000 work-order transactions
npm run provision:employee-logins
```

## Storage

`data/store.js` is the single data access layer. Everything is documents in named collections (`users`, `work_orders`, `parts_inventory`, `approval_requests`, …; full list in `normalizeData()`). API: `getAll/getById/create/update/remove` + `getRawData/replaceData`.

`lib/sqlite-engine.js` backs it with Node's built-in `node:sqlite`, writing a JSON snapshot beside the DB on every save.

- Local DB: `%LOCALAPPDATA%\AE-DMS\shop.sqlite` (falls back to `data/AE-DMS/` off-Windows); override with `DMS_SQLITE_PATH`.
- Cloud (Render disk): `/data/shop.sqlite`.
- **`data/data.json` is a first-boot seed only.** Never treat it as live state; it does not overwrite an existing DB.

## Auth and access control

`lib/portals.js` is the authority for who can do what. Model: **role → department → portal → grants**.

- 6 portals: `service`, `parts`, `stores`, `hr`, `gm`, `fo`.
- ~20 roles (`ROLE_GENERAL_MANAGER`, `ROLE_TECHNICIAN`, `ROLE_PARTS_CLERK`, …), each mapped to a grant set per portal via `GRANT` (`view`, `edit`, `approval`, `request`, `edit_price`, `pos_sale`, `view_payroll`, …).
- Key helpers: `grantsForRole`, `hasGrant`, `canEnterPortal`, `portalForPath`, `homePathForRole`, `accessiblePortals`.

Adding a role or permission means editing `lib/portals.js`, not sprinkling checks in routes.

Two independent login bypasses — do not conflate them:
- `DISABLE_LOGIN=1` env → dev-only bypass, injects a fake session user with `BYPASS_ROLE`.
- Store setting `auth_settings.login_disabled` → runtime "open login" toggle, cached in `lib/login-auth.js`.

## Request pipeline (app.js, ~3000 lines)

Order matters; middleware in `app.js` runs before any router:

1. helmet / body parsers / session / static
2. dev-bypass session + `res.locals` population (currentUser, portal, grants, `canGrant()` for views, pending approval count)
3. `/healthz` (unauthenticated, reports storage paths)
4. `/auth` behind `authLimiter` (20 req / 15 min)
5. auth gate — API paths get 401 JSON, pages redirect to `/auth/login`
6. portal gate — `canEnterPortal` by path; special cases for `/approvals`, `/transactions`, `/helper`
7. work-order field forcing — server overwrites `service_advisor` and `branch` from the session for frontline roles
8. branch isolation — frontline roles get 403 on work orders outside their assigned branch
9. delete-password gate on any `POST .../delete`

Then routers mount in `routes/*.js`, most wrapped in `requireRole` / `requireAnyRole` / `requireGrant` / `requirePortalAccess`.

## Layout

- `routes/` — one router per domain, thin; business logic lives in `lib/`.
- `lib/` — domain modules (parts inventory controller, finance ledger, work-order status, comeback metrics, PDF/receipt builders, numbering).
- `views/` — EJS, one subdirectory per portal/domain, shared `views/partials/`.
- `app-admin.js` / `app-gm.js` — 3-line wrappers that set a port and `require('./app')`. Not separate apps.

## Domain conventions

- **Branches** (`lib/branches.js`): 7 operational branches — Carx2, Carmen, CebuCity, Lapux2, Bogo, Toledo, ITPark. `CebuCity` is the flagship (SA/SR FTE lock). Old names still appear in imported data; always run values through `canonicalizeBranchName()`. `Proposed Location` is the pipeline/pre-operational branch.
- **Document numbers** are generated by dedicated `lib/parts-*-number.js` modules by scanning existing rows for the max sequence — e.g. `PTN-YYYYMMDD-000001`. Use them; don't hand-roll IDs.
- **Work order status** (`lib/work-order-status.js`): hold statuses are `waiting-parts`, `break`, `on-other-priority`.
- **Approvals**: cross-portal requests land in the `approval_requests` collection, surfaced at `/approvals` to any role holding the `approval` or `request` grant.

## Deploy

`render.yaml` — Docker web service, 2 GB disk at `/data`, health check `/healthz`, `SESSION_SECRET` auto-generated. `SECURE-OPERATIONS.md` has the Windows/NSSM always-on and backup-scheduling procedures.

Invoice/BIR fields (`INVOICE_*`) and `SESSION_SECRET` come from env — see `.env.example`.
